# Changelog — afrotickets-backend-gcp

All notable changes to the Cloud Run + Cloud SQL variant, in order.

## [1.21.0] — Organizer identity/business document upload & review

- **New `organizer_documents` table and upload flow.** An organizer can now submit supporting documents (`identity`, `business_registration`, or `other`) via `POST /organizer/documents` (multipart, JPEG/PNG/WebP/PDF, 10MB max), list their own submissions via `GET /organizer/documents`, and download one back via `GET /organizer/documents/:id/file`. This was previously a checklist item with zero code — onboarding only ever collected a name/country/settlement method text field.
- **Kept deliberately separate from event images.** A new `utils/organizerDocumentStorage.js` stores files in `private-uploads/organizer-documents/`, NOT the existing `uploads/` directory that `imageStorage.js` uses — that directory is mounted with `express.static` and served publicly to anyone with the URL. An ID scan or business registration number is real PII and must never be reachable by a guessed or leaked URL; every document read goes through an authenticated route that checks the requester is the owning organizer or a platform admin, and `storage_path` is stripped from every API response (organizers and admins alike only ever see metadata: type, filename, mime type, status, timestamps).
- **Admin review, independent of organizer approval.** New `GET /admin/organizers/:id/documents`, `GET /admin/organizers/:id/documents/:docId/file`, `POST .../approve`, `POST .../reject` (with a reason). Reviewing a document does not automatically approve or reject the organizer overall — verification_status is still a separate, deliberate admin decision, with document review as one input to it. `GET /admin/organizers/pending` and the existing suspended-organizers listing now also carry a lightweight per-organizer document summary (type/status/filename/upload time — no storage_path) so an admin can see what's been submitted without an extra round trip.
- New `organizer.document_approved`/`organizer.document_rejected` notification templates.
- **Verified end-to-end against a real running server and a real local Postgres database.** Registered an organizer and a platform admin, then exercised: an invalid `documentType` (400), a disallowed mime type — a `.txt` file — (400), a missing file (400), two valid uploads (identity as JPEG, business_registration as PDF — both 201, no `storage_path` in the response). Confirmed the organizer's own download returns byte-identical content to what was uploaded. Confirmed the admin pending-organizers listing carries the document summary, admin's direct per-organizer document list matches, and admin file download also returns byte-identical content. Approved one document, rejected the other with a reason, and confirmed a second approval attempt on an already-reviewed document correctly 409s. **Security boundaries specifically tested**: a second organizer cannot list or download the first organizer's documents (empty list, 404 on direct file access by ID); a plain buyer role gets 403 on both the upload and admin review routes; the private storage directory is confirmed NOT reachable through the public `/uploads` static route (404); and the files on disk were confirmed to actually live outside the `uploads/` tree (`private-uploads/organizer-documents/`, sibling to it, not inside it). Mirrored identically on the SQLite variant with the same test sequence against a real local SQLite database.

## [1.20.0] — Seat-generation input validation

- **`POST /organizer/events/:id/seats` now validates its inputs before doing any arithmetic or DB work.** Previously `rows` and `seatsPerRow` were only checked with a truthiness test (`!rows || !seatsPerRow`) and then multiplied together — a non-numeric, negative, zero, or fractional value slipped straight through. Concretely: `rows: "abc"` made `seatCount` `NaN`, which is never `> quantity_total` (all `NaN` comparisons are false) and never runs a loop iteration (`0 < NaN` is false) — so the route created **zero seats** but still replied `201 Generated NaN seats in <section>`. `rows: -1` with a large `seatsPerRow` had the identical silent-no-op failure: a positive-looking `seatCount` that passed the quantity check, followed by a loop that never executed because `0 < -1` is false. Both are now rejected with a `400` before anything runs.
- New `validateSeatGeneration` middleware in `security.js`, following the same pattern as `validateEventCreation`/`validateTicketTypeCreation`: `rows` and `seatsPerRow` must each be whole numbers between 1 and 1,000 (`Number.isInteger`, no coercion from strings), `sectionName` must be 1-100 characters from a safe charset, and `tier` (if provided) must be 1-40 characters from the same kind of charset already used for event categories. The 1,000×1,000 bounds keep the largest possible `seatCount` (1,000,000) in line with the existing ticket-type `quantity` cap from v1.13.0, so this can't be used to force a runaway insert loop even against a ticket type with a large `quantity_total`.
- The pre-existing `seatCount > quantity_total` check and the unique `(event_id, section_name, row_label, seat_number)` DB constraint (which already rejected a duplicate seat-generation call with a `500`) are unchanged — this only closes the gap in front of them.
- **Verified end-to-end against a real running server and Postgres database** (not just unit-level): registered an organizer, approved it via direct DB promotion, created an event with a 500-quantity ticket type, then exercised every rejected case from the audit finding directly — `rows: "abc"` (the exact NaN scenario), `rows: -1` with `seatsPerRow: 100000` (the exact silent-negative scenario), `rows: 2.5` (fractional), `rows: 0`, `rows: 1001` (over the new cap), a missing `sectionName`, and an invalid `tier` value — all correctly returned `400` with a clear message. A valid request (`rows: 5, seatsPerRow: 10, tier: "vip"`) still succeeded and inserted exactly 50 rows into `event_seats`, confirmed by a direct `SELECT count(*) ... GROUP BY section_name, tier`. A subsequent valid-shaped request that would exceed the ticket type's `quantity_total` (100×10 = 1,000 seats against a 500-quantity ticket type) was still correctly rejected by the existing check. Mirrored identically on the SQLite variant and re-ran the same nine cases against a real local SQLite database with identical results.

## [1.19.0] — Backups, monitoring, and alerting

- **`/health` now actually checks the database**, not just "the process is up." Previously it returned `{"ok": true}` unconditionally — a Cloud Monitoring uptime check watching it could never detect a dead Cloud SQL connection (network blip, instance restart, exhausted pool). Now it runs `SELECT 1` and returns `503` with `{"ok": false, "db": "down"}` on failure, `200` with `{"ok": true, "db": "ok"}` on success. This is the endpoint the new uptime check (see below) is configured against.
- **Fixed a real crash bug found while testing the above**: an error on an *idle* pooled Postgres connection (Cloud SQL terminating it for maintenance, a network blip, the instance restarting) was an unhandled `'error'` event on the `pg` `Pool`, which crashed the entire Node process — confirmed by actually stopping the local Postgres instance mid-run and watching the server die. `pool.on('error', ...)` now logs and lets the process continue; a connection actively running a query still fails normally as a rejected promise to whichever request triggered it. This was a pre-existing gap, not something this feature introduced — it surfaced specifically because this was the first time `/health` was made to genuinely depend on the database being reachable, which is exactly the scenario production monitoring needs to survive.
- **Cloud SQL automated backups + point-in-time recovery enabled on production** (`afrotickets-db`): daily backups plus WAL-based point-in-time recovery, 7-day retention on both. Infrastructure config, not application code — see `backups-monitoring-alerting-v1.19.0.md` for the exact commands run and current retention settings.
- **Cloud Monitoring uptime check + alerting policies configured on production**: an uptime check against `/health`, and alert policies for uptime-check failure, an elevated Cloud Run 5xx rate, and Cloud SQL disk utilization — all routed to a single email notification channel. See `backups-monitoring-alerting-v1.19.0.md` for what's actually wired up and how to verify or extend it.
- **Verified end-to-end**: booted the server against a real local Postgres instance, confirmed the healthy path (`200`, `db: "ok"`); stopped Postgres mid-run and confirmed `/health` correctly returns `503`/`db: "down"` **and the server process survives** (this is the fix above actually holding); restarted Postgres and confirmed `/health` recovers to `200` without needing to restart the Node process. Mirrored the health-check logic on the SQLite variant (`db.prepare('SELECT 1').get()`) and confirmed its healthy path — SQLite has no equivalent idle-connection-error failure mode, so no pool fix was needed there.

## [1.18.0] — Resale labeling and per-event opt-out

- **Tickets now carry `origin`**: `'primary'` (the default — every ticket ever minted before this migration is correctly labeled with no backfill needed) or `'resale'`, set explicitly by `routes/resale.js` on the replacement ticket it mints after a resale sale. Previously invisible in both the data model and every API response; now returned on `GET /api/tickets/mine`.
- **Per-event resale opt-out**: new `events.resale_disabled_at` (NULL by default, matching today's behavior — resale globally available on any valid ticket). An organizer can pass `resaleEnabled: false` at event creation (`POST /organizer/events`), or toggle it later via `PATCH /organizer/events/:id` with `{ "resaleEnabled": true|false }` — this toggle is exempt from the usual "locked once tickets have sold" rule that guards `venue`/`city`/`startsAt`/etc., since it only affects future listings, never a ticket holder's existing expectations.
- **What the opt-out actually blocks**: `POST /api/resale/list` now checks the ticket's event and returns `403` if the organizer has disabled resale for it. It only blocks a *new* listing — turning resale off never retroactively cancels a listing that's already active, so a seller who listed in good faith before the organizer's decision isn't caught out.
- No changes to buying an already-active listing, cancelling a listing, or any other resale endpoint.
- **Verified end-to-end against real running servers on both variants** (fresh SQLite / a local Postgres instance, not mocks): confirmed a ticket bought at retail carries `origin: "primary"`; confirmed the ticket minted for a resale buyer carries `origin: "resale"` and the seller's old ticket is correctly `invalidated`; confirmed creating an event with `resaleEnabled: false` sets `resale_disabled_at`, and listing a ticket on it returns 403; confirmed `PATCH .../resaleEnabled: true` clears it and listing then succeeds; confirmed the toggle works both ways on an event that already has tickets sold (not blocked by the sold-ticket edit lock, unlike venue/date fields). All scenarios passed identically on both `afrotickets-backend` (SQLite) and `afrotickets-backend-gcp` (Postgres).

## [1.17.0] — Organizer suspension

- **New organizer status: `suspended`**, distinct from `rejected`. Reject is a pre-approval decision on an organizer who was never live; suspend pauses an already-`approved` organizer — e.g. a dispute pattern or an open fraud signal worth investigating — without deleting their account, their history, or unpublishing events already on sale. New admin endpoints: `POST /api/admin/organizers/:id/suspend` (requires the organizer is currently `approved`; body `{ reason }`), `POST /api/admin/organizers/:id/reactivate` (requires `suspended`, returns to `approved`), and `GET /api/admin/organizers/suspended` to list them, mirroring the existing `/organizers/pending` queue.
- **Independent of payout freezing.** `payouts_frozen_at`/`payouts_frozen_reason` (v1.14.0) already exist for the money-only case — suspending an organizer does not automatically freeze their payouts, and freezing payouts does not suspend them. An admin decides each separately.
- **What suspension actually blocks**, enforced in `routes/organizers.js` via a new `blockIfSuspended()` check: creating a new event, editing an existing event (`PATCH /events/:id`), generating seats, and uploading/removing a cover image all now return `403` for a suspended organizer. Cancelling or postponing an existing event, and every read-only endpoint (`GET /me`, `/events/mine`, event analytics), stay open — a suspended organizer can still protect their existing ticket holders and see their own status, they just can't grow their footprint further while under review.
- New columns `organizers.suspended_at`, `organizers.suspension_reason`. No changes to any other table.
- New notification templates: `organizer.suspended`, `organizer.reactivated`.
- **Verified end-to-end against real running servers on both variants** (fresh SQLite file / a local Postgres instance, not mocks): confirmed suspending a `pending` (not-yet-approved) organizer is rejected with 409; confirmed a suspended organizer gets 403 on create/edit/seat-generation/image-upload but 200 on postpone and on reading their own profile; confirmed `GET /organizers/suspended` lists them with settlement details decrypted for admin review, matching the existing `/organizers/pending` pattern; confirmed reactivation returns them to `approved`, a second reactivate attempt 409s, and they can create events again immediately after; confirmed the full `suspended → reactivated` sequence appears in the audit log. All scenarios passed identically on both `afrotickets-backend` (SQLite) and `afrotickets-backend-gcp` (Postgres).

## [1.16.0] — Ticketmaster event discovery aggregation

- **Discovery only, never a purchase path.** `GET /api/discover/events` (`keyword`, `city`, `countryCode`, `page`, `size`) pulls events from Ticketmaster's public Discovery API and returns them alongside AfroTickets' own listings to make the catalog feel fuller. AfroTickets never sells or processes payment for these — each result carries an `externalUrl` that sends the user to Ticketmaster's own checkout. Deliberately a separate route (`/api/discover`, not a param under `/api/events`) so it can never collide with `/api/events/:id`'s numeric-id lookup and so consumers can tell at a glance this is external, not-purchasable-here content.
- **"Real when configured, honest fallback otherwise"**, same pattern as M-Pesa B2C and AfroGuide's AI search: with no `TICKETMASTER_API_KEY` set, the endpoint returns `{"source": "none", "events": []}` rather than fabricating events. A live Ticketmaster API failure degrades the same way (`{"source": "error", "events": []}`, still a 200) rather than a raw 500 breaking a discovery page.
- **Impact.com affiliate link wrapping**, `buildAffiliateLink()`: when `IMPACT_TRACKING_LINK_TEMPLATE` is configured (a URL template with a `{url}` placeholder), every `externalUrl` is wrapped for affiliate tracking. Without it, links point straight at Ticketmaster — untracked but fully functional. The exact tracking-link shape is specific to a signed-up Impact.com publisher account, so this takes a template rather than guessing at parameters that would look real but aren't.
- **In-memory response cache** (`AGGREGATION_CACHE_TTL_MS`, default 10 minutes) keyed by search params — Ticketmaster's free Discovery API tier has a real daily quota (5,000 requests/day), so identical repeat searches don't re-hit the live API within the cache window. Per-process, not shared across Cloud Run instances or persisted — a cold cache on scale-out just costs one extra live call, never stale/wrong data.
- New `aggregationLimiter` (30 requests/15min per IP) in `security.js`, same reasoning as the existing `afroguideLimiter`: bounds cost/quota exposure from a single client hammering an endpoint that calls a paid/quota-limited external API.
- New env vars: `TICKETMASTER_API_KEY`, `AGGREGATION_CACHE_TTL_MS`, `IMPACT_TRACKING_LINK_TEMPLATE`.
- No database schema changes — this feature has no persisted state.
- **Verified end-to-end against real running servers on both variants**, not mocks: confirmed the honest empty-result fallback with no API key configured; confirmed `keyword`/`city`/`countryCode` input validation rejects malformed input (oversized keyword, non-ISO country code) with 400; confirmed the rate limiter returns 429 after 30 requests; confirmed a genuinely live call to Ticketmaster's real API with an invalid key degrades to the honest `source: "error"` response with a 200, not a crash. Verified the response normalization and Impact.com link-wrapping logic against a realistic Discovery API response shape (own parsing code under test, not a live financial transaction) — correct venue/city/country/price-range extraction, correct widest-16:9-image selection, and correct URL-encoding through the affiliate template. Verified the in-memory cache actually prevents a second live call for an identical repeat search within the TTL window. All scenarios passed on both `afrotickets-backend` (SQLite) and `afrotickets-backend-gcp` (Postgres).

## [1.15.0] — Staging environment + environment identification

Directly motivated by the v1.14.0 deploy, where a stale-source deploy went unnoticed at first because there was no way to tell from the response alone which build was actually running — this doesn't fix that specific failure mode, but it removes "which environment am I even hitting" as a source of confusion once a second (staging) URL exists.

Staging gets its own freshly-generated secrets (`*-staging` suffix) rather than reusing production's, specifically so a staging-issued session JWT is never valid against production and vice versa. ## [1.14.0] — Organizer payouts: ledger, admin review, freeze, and reserve holdback

- New `payouts` table — one row per `(event_id, kind)`, `kind` is `'initial'` (proceeds minus a held-back reserve, payable once the event has happened) or `'reserve_release'` (the reserve itself, released after a hold window, net of any refunds during it). `UNIQUE(event_id, kind)` makes the auto-generation sweep idempotent: it can safely re-scan every event on every run without ever double-creating a payout, the same idempotency principle as every `CREATE TABLE IF NOT EXISTS` migration and the v1.13.0 retention sweep. Like refunds, a payout is always generated as a system request first and decided second by a `platform_admin` — money never moves without a human in the loop.
- **Payout trigger**: proceeds from an event's paid orders become payable once the event's `starts_at` has passed — not before.
- **Gross proceeds**, `utils/payoutCalculator.js`: computed from `orders.subtotal_cents` (not `total_cents` — `fee_cents` is the platform's own cut, `tax_cents` isn't organizer money) with proportional refund clawback per order (`refundedFraction = min(1, refunded_cents / total_cents)`), computed in JS rather than SQL float arithmetic, and recomputed fresh at both initial-payout time and reserve-release time so refunds occurring during the hold window are automatically reflected. Cancelled events never generate a payout — cancellation already opens refund requests for every paid order (v1.12.0), so any gross there is transient.
- **Reserve holdback**: `PAYOUT_RESERVE_RATE` (default 10%) of gross is held back and released `PAYOUT_RESERVE_HOLD_DAYS` (default 14) after the event, net of refunds that happened during the hold: `release = max(0, recomputedGross - initialPayout.amount_cents)`. If refunds during the hold absorbed the whole reserve (or the initial payout amount was already 0), the `reserve_release` row is inserted already `succeeded` with `amount_cents = 0` rather than left around for an admin to approve nothing — same principle applied to a zero-gross initial payout.
- New `utils/payoutScheduler.js`: an automated sweep (runs once at boot, then on `PAYOUT_SWEEP_INTERVAL_MS`, default hourly) that generates `initial` payouts for newly-eligible events and `reserve_release` payouts for initial payouts an admin has already resolved (`succeeded` or `manual_required`) once the hold window has passed.
- **M-Pesa B2C ("Business to Customer")** support in `utils/mpesaProvider.js` — a genuinely different Daraja API product from the existing STK Push (C2B) integration, requiring its own initiator identity, shortcode, and an RSA-encrypted "security credential" (`crypto.publicEncrypt` against Safaricom's public certificate). Gated by `isB2CConfigured()`, checking all six required env vars independently of the existing STK Push credentials — a deployment with only STK Push configured is honest about falling back to `manual_required` rather than faking a disbursement.
- New `routes/payouts.js`: `GET /api/payouts/mine` (an organizer's own payout history) and the M-Pesa B2C result webhook (`POST /api/payouts/webhook/mpesa-b2c/:secret`) that finalizes a payout from `approved_processing` to `succeeded`/`failed` when Safaricom's async callback arrives — B2C only confirms the request was *accepted* at dispatch time, exactly mirroring the existing STK Push pattern. `processPayoutWithProvider()` is exported for `admin.js`'s approve route to call, the same reuse pattern as `processRefundWithProvider`.
- Admin review queue in `admin.js`: `GET /api/admin/payouts/pending`, `POST /api/admin/payouts/:id/reject`, `POST /api/admin/payouts/:id/approve`. Approval uses the same atomic conditional-UPDATE claim as refund approval (`WHERE id = $2 AND status = 'requested'`, checked by rows-affected) so a double-click or two admins racing can't both dispatch the same payment.
- **High-risk payout freeze**: new `organizers.payouts_frozen_at` / `payouts_frozen_reason` columns, `POST /api/admin/organizers/:id/freeze-payouts` and `.../unfreeze-payouts`. Checked before the atomic approval claim (not before payout-request creation), so the scheduler keeps generating and queuing `requested` payouts for a frozen organizer — nothing is silently lost — only the actual approval/dispatch step is blocked until an admin unfreezes.
- New env vars: `PAYOUT_RESERVE_RATE`, `PAYOUT_RESERVE_HOLD_DAYS`, `PAYOUT_SWEEP_INTERVAL_MS`, `MPESA_INITIATOR_NAME`, `MPESA_INITIATOR_PASSWORD`, `MPESA_B2C_SHORTCODE`, `MPESA_B2C_CERT_PATH`, `MPESA_B2C_RESULT_URL`, `MPESA_B2C_TIMEOUT_URL`.
- **Verified end-to-end against a real running server and a real local Postgres database**, not mocks: backdated a real event past its `starts_at` with a real paid order and confirmed the sweep generated exactly the expected `initial` payout (gross minus reserve); approved it with no B2C credentials configured and confirmed a genuine `manual_required` result, not a faked success; confirmed a second approval attempt on the same payout is rejected with a clean 409; re-ran the sweep and confirmed it correctly generated the matching `reserve_release` payout only once the hold criteria were met, and that re-running the sweep afterward never duplicated either row. Froze an organizer and confirmed approval of a pending payout was blocked with 409 while the sweep kept generating requests regardless; unfroze and confirmed approval then succeeded. Rejected a payout and confirmed its status/reason were recorded. Fully refunded an order after its initial payout was approved and confirmed the resulting `reserve_release` was correctly zeroed out and auto-marked `succeeded` rather than left pending; partially refunded another and confirmed the release amount was clawed back proportionally. Confirmed a cancelled event never generates a payout. Confirmed the organizer's own `/api/payouts/mine` view returns the full, correct history. All scenarios passed on both `afrotickets-backend` (SQLite) and `afrotickets-backend-gcp` (Postgres).

## [1.13.0] — Hardening: rate limiting, input validation, audit-log immutability, PII encryption, data retention

- **PII encryption at rest**: new `utils/piiCrypto.js` — AES-256-GCM, random 12-byte IV per value, stored as `base64(iv || authTag || ciphertext)` in the existing TEXT column (no schema change needed). `users.phone` and `organizers.settlement_account` are now encrypted on write and decrypted only at the points that legitimately need the real value (an organizer viewing their own profile, a platform admin reviewing onboarding, and — critically — `utils/notify.js` decrypting `phone` before handing it to the SMS/WhatsApp provider, since a provider must receive a real number, not ciphertext). `email` is deliberately excluded from scope: it's looked up by exact match everywhere (login, transfer-by-email, admin lookups), and AES-GCM's random IV means the same plaintext encrypts differently every time — indexing it would need a separate deterministic hash, out of scope here. `decrypt()` tolerates legacy plaintext or malformed input by returning it unchanged, so a rolling deploy never 500s on a pre-encryption row. Mirrors the existing `JWT_SECRET || 'dev-secret...'` fallback pattern with `PII_ENCRYPTION_KEY || 'dev-pii-key-change-me-in-production'` for local/dev.
- **Rate limiting on ticket transfer and check-in**, keyed by user id (not IP, since both require auth) so one person's traffic never throttles anyone sharing their network: `transferLimiter` (10 transfers / 15 min) on `POST /api/tickets/:id/transfer`, and a generous `checkinLimiter` (120 requests / minute) on `POST /api/checkin/scan` and `POST /api/checkin/sync` — sized for real door staff scanning in rapid bursts, but still bounding a compromised scanner or scripted client fishing for valid ticket codes.
- **Input validation on event and ticket-type creation** (`POST /api/organizer/events`): `validateEventCreation` and `validateTicketTypeCreation` middleware in `security.js` reject an oversized/malformed `name`, `category`, `description`, `venue`/`city`/`country`, a `startsAt` that isn't a real future date, a non-ISO `currency` code, and (per ticket type) a non-numeric/negative `price` or a non-integer/out-of-range `quantity` — all before an event row (and its dependent `ticket_types` rows) is ever created.
- **DB-level audit-log immutability**: a real database trigger — a Postgres `BEFORE UPDATE OR DELETE` trigger function, a SQLite `BEFORE UPDATE`/`BEFORE DELETE` trigger pair — now rejects any mutation of `audit_log`, at the database layer, regardless of who issues it or how. This replaces "nothing in the app calls UPDATE/DELETE on it" (a convention) with an actual guarantee a compromised credential or a bad migration can't get around.
- **Data retention / deletion automation**:
  - `POST /api/auth/delete-account` (self-service, password-confirmed): anonymizes the user's row in place (name, email, phone scrubbed; password hash replaced with an unusable random one; MFA disabled) rather than a hard DELETE, since `orders`/`tickets`/`refunds`/`audit_log` all reference `user_id` and this platform is required to keep that financial/legal history. Revokes every session. Same "flag, don't delete" pattern already used for a cancelled event or removed ticket type.
  - New `utils/dataRetention.js`: an automated sweep (runs once at boot, then on a configurable interval — `RETENTION_SWEEP_INTERVAL_MS`, default 24h) that deletes expired email/phone/password-reset verification records (`VERIFICATION_RETENTION_DAYS`, default 30), long-revoked/expired sessions (`SESSION_RETENTION_DAYS`, default 90), and old notifications (`NOTIFICATION_RETENTION_DAYS`, default 180). `audit_log` is deliberately never a target — it's the platform's record of what happened, not data with a natural expiry, and the new immutability trigger above would reject a delete against it anyway.
- **Verified end-to-end against real running servers and real databases, not mocks**: confirmed a registered phone number and an organizer's settlement account are stored as ciphertext in the actual database row (not just asserted from the encryption function in isolation), then confirmed `utils/notify.js` correctly decrypts the real phone number before handing it to a (mocked-at-the-network-boundary) SMS send — proving the fix end-to-end, not just the crypto unit. Hammered `/tickets/:id/transfer` and `/checkin/scan` past their limits and confirmed a real 429 on both. Sent malformed event/ticket-type payloads (bad category, past date, negative price, non-integer quantity) and confirmed each is rejected with 400, while a valid payload still succeeds with 201. Ran `UPDATE`/`DELETE` directly against `audit_log` on both a live Postgres and a live SQLite database and confirmed the trigger rejects both. Seeded genuinely expired verification/session/notification rows, ran the real sweep function, and confirmed exactly those rows were deleted while `audit_log` was untouched. Deleted a real account via the endpoint and confirmed login with the old email afterward correctly fails. All scenarios passed on both `afrotickets-backend` (SQLite) and `afrotickets-backend-gcp` (Postgres).

## [1.12.0] — Event management: edit, cancel, postpone, cover image

- **Edit** (`PATCH /api/organizer/events/:id`): `name`, `category`, and `description` are always editable. `venue`, `city`, `country`, `currency`, and `startsAt` are editable only while zero tickets have actually sold (checked against `SUM(ticket_types.quantity_sold)`, not just reservations) — once a single ticket sells, those fields are locked and the error for `startsAt` specifically points at `/postpone`, since a date change needs to notify ticket holders and a silent PATCH shouldn't do that.
- **Cancel** (`POST /api/organizer/events/:id/cancel`): sets the event to `cancelled` (blocking further checkout and removing it from public listings, since both already gate on `status = 'published'`), invalidates every live ticket (which alone blocks check-in/resale — both already gate on `status = 'valid'`), removes any active resale listings, and cancels any still-`pending_payment` orders. For every `paid`/`partially_refunded` order, it opens a refund request on the customer's behalf for the full remaining balance — reusing the exact v1.10.0 refunds table/workflow, so an admin still has to approve it (money never moves without that review) but the customer doesn't have to ask when the organizer caused the cancellation. Notifies every affected ticket holder, distinguishing "a refund was requested for you" from a plain cancellation notice.

A cancelled event can't be postponed (or edited).

## [1.11.0] — Account access & security: email/phone verification, password reset, MFA, session revocation

- **Sessions are now tracked, not just signed.** A new `sessions` table backs every login/register — the JWT carries a `jti` pointing at its row, so a session can actually be revoked before its 7-day expiry (a bare stateless JWT can't be). `requireAuth` checks the session on every request (not revoked, not expired) in addition to verifying the JWT signature.
  - `POST /api/auth/logout` — revokes the current session.
  - `GET /api/auth/sessions` — lists a user's sessions (device/user-agent, created/last-seen, which one is "current").
  - `POST /api/auth/sessions/:id/revoke` — revoke one specific session ("sign out this device").
  - `POST /api/auth/sessions/revoke-all` — sign out everywhere else (or everywhere, with `includeCurrent: true`).
- **Email verification**: `users.email_verified_at` + a token-based flow. Registering sends a verification email (or logs it, when no email provider is configured — the same honest fallback pattern used for payments/notifications). `POST /api/auth/verify-email`, `POST /api/auth/resend-verification`. Tokens are single-use, expire in 24h, and are stored only as a sha256 hash — a DB leak can't be replayed.
- **Phone verification**: `users.phone_verified_at` + a 6-digit SMS code. `POST /api/auth/send-phone-verification`, `POST /api/auth/verify-phone` — expires in 10 minutes, capped at 5 incorrect attempts before a new code is required.
- **Password reset**: `POST /api/auth/forgot-password` always returns the same generic response whether or not the email exists, so it can't be used to enumerate accounts. `POST /api/auth/reset-password` consumes a single-use, 1-hour token and — since a reset implies the old credential may have been compromised — revokes every existing session for that account. Also added `POST /api/auth/change-password` (requires the current password; revokes every *other* session, keeping the current one alive).
- **MFA (TOTP)**: `POST /api/auth/mfa/setup` (returns a secret + otpauth URL for an authenticator app), `POST /api/auth/mfa/enable` (requires one valid code before turning it on, so a typo or lost setup can't lock someone out; returns 8 one-time backup codes shown exactly once), `POST /api/auth/mfa/disable` (requires the account password). Once enabled, `/login` no longer returns a session directly — it returns a 5-minute challenge token, which `POST /api/auth/mfa/verify` exchanges for a real session after a valid TOTP code or an unused backup code. Backup codes and MFA secrets are only ever stored hashed/as-configured, never re-displayed.
- Every sensitive action here (verification, reset, MFA enable/disable) is audit-logged and sends a real notification, and password/MFA changes explicitly warn the user if it wasn't them.
- **Verified end-to-end against real running servers and real databases**, not mocks: registered a user and pulled the real verification token/code from the actual delivery path (the same console-log fallback production uses when no provider is configured) to complete email verification, phone verification, and password reset exactly the way a user would from their inbox/SMS. Generated real TOTP codes with `otplib` to enable MFA, complete a login challenge, and confirm a wrong code and a reused backup code are both rejected. Confirmed a revoked/logged-out session token is rejected by `requireAuth` immediately (not just after the JWT's own expiry), while other sessions on the same account are untouched. Re-ran the existing checkout, refund, and admin-queue tests afterward to confirm the new session check in `requireAuth` didn't break any existing authenticated route. All scenarios passed on both `afrotickets-backend` (SQLite) and `afrotickets-backend-gcp` (Postgres).

## [1.10.0] — Refunds and disputes (production-readiness audit, critical finding #2)
- New `refunds` table and `orders.refunded_cents` running-total column. A refund is always a **request first, decision second** — no money moves without a `platform_admin` approving it, which is the actual dispute-workflow the audit asked for.
- Customer-facing: `POST /api/refunds` (request a full or partial refund on a `paid`/`partially_refunded` order — validated against the order's real remaining balance, blocks a second request while one is already pending), `GET /api/refunds/mine`.
- Admin-facing: `GET /api/admin/refunds/pending`, `POST /api/admin/refunds/:id/approve`, `POST /api/admin/refunds/:id/reject` — same review-queue pattern as organizer/event approval.
- **Approval uses the exact same atomic-conditional-UPDATE pattern as the v1.9.0 oversell fix**: `UPDATE orders SET refunded_cents = refunded_cents + $1 WHERE id = $2 AND refunded_cents + $1 <= total_cents`, inside a transaction, checked by rows-affected. Two admins approving two different pending refund requests on the same order at the same instant can't jointly refund more than the order actually cost — one gets a clean 409 instead of a double-refund.
- A full refund (amount reaches the order's total) invalidates every ticket on the order (`status = 'invalidated'`) and sets `orders.status = 'refunded'` — this automatically blocks both check-in and resale, since both already gate on `status = 'valid'`. A partial refund leaves the order `partially_refunded` and the ticket(s) valid — the customer keeps their ticket.
- Provider dispatch is honest about what's actually wired up: mock provider refunds instantly (mirrors the original mock charge flow); Stripe calls the real Refunds API (`stripe.refunds.create`, with Stripe's own request-level idempotency key so a retry can't double-refund); **M-Pesa is flagged `manual_required` rather than faked** — Safaricom's B2C reversal API needs a separate certificate-encrypted security credential, initiator name, and B2C shortcode this integration was never configured with, and pretending to reverse a real payment without them would be dishonest about money actually moving.
- If the provider genuinely fails after `refunded_cents` was already committed (proved with a real blocked network call to `api.stripe.com`, not a stub), the reservation is rolled back so a failed attempt doesn't permanently eat into the order's refundable balance.
- **Verified with real concurrency and real failure modes**: full refund → ticket invalidation → resale/check-in now correctly blocked; partial refund → ticket stays valid; rejection → order/ticket state unchanged; over-the-remaining-balance request → 400; two concurrent approvals on the same order that would jointly overspend the total → exactly one 200, one clean 409, `refunded_cents` never exceeds `total_cents`. Genuine Stripe network failure → refund marked `failed`, `refunded_cents` correctly rolled back to 0. M-Pesa-settled order → refund correctly marked `manual_required`, no money-movement faked. Every scenario passed on both `afrotickets-backend` (SQLite) and `afrotickets-backend-gcp` (Postgres).

## [1.9.0] — Fixed the oversell race condition (production-readiness audit, critical finding #1)
- `validateAndResolveItems()` did a plain `SELECT` outside any lock to check `quantity_total - quantity_reserved - quantity_sold`, then a separate, later `UPDATE ticket_types SET quantity_reserved = quantity_reserved + $1` never re-checked capacity — two simultaneous checkouts for the last unit(s) could both pass the check and both reserve, overselling the event. Same gap existed for seats (`event_seats.status`).
- Fixed by replacing the unconditional reservation `UPDATE`s in `reserveAndCreateOrder()` with atomic conditional `UPDATE`s, run inside the existing transaction, that check and claim capacity in a single statement:
  - General admission: `UPDATE ticket_types SET quantity_reserved = quantity_reserved + $1 WHERE id = $2 AND quantity_reserved + quantity_sold + $1 <= quantity_total RETURNING id` — 0 rows back means someone else already claimed the remaining inventory, and the whole order (and any other items already reserved in the same cart) rolls back with a clean `409`.
  - Seats: `UPDATE event_seats SET status = 'reserved' WHERE id = $1 AND status = 'available' RETURNING id`, same all-or-nothing rollback on a lost race.
  - `validateAndResolveItems()`'s original `SELECT` is kept as a fast pre-check for a good error message on obviously sold-out items, but it is no longer the authority — the atomic `UPDATE` inside the transaction is.
  - 409 responses from a lost race now propagate their real status code (previously flattened to a generic 500) across all three checkout paths (mock, M-Pesa, Stripe).
- **Verified with genuine concurrency, not a simulation**: seeded a ticket type and a seat each with capacity for exactly 1, then fired 10 truly concurrent requests at each — via real parallel HTTP requests against a live server backed by a real local Postgres instance for the GCP/Postgres variant, and via 10 separate OS processes each opening their own SQLite connection to the same database file for the SQLite/Railway variant (the scenario that actually exercises multi-process file-level contention, since a single Node process serializes requests with no `await` gap between them). In every run: exactly 1 winner, 9 clean 409s, and the database ended up exactly consistent (`quantity_reserved + quantity_sold <= quantity_total`; the seat claimed exactly once).
- Mirrored identically in both `afrotickets-backend` (SQLite) and `afrotickets-backend-gcp` (Postgres).
